# TinyOS

A bare-metal micro-kernel for the RP2040 (tested on the Pimoroni Tiny 2040, 8MB flash variant), written from scratch in C and ARM assembly — no HAL, no RTOS, no `pico-sdk` linked in. Every peripheral (clocks/PLLs, the USB device controller, the QSPI flash) is driven directly by register writes or by calling the RP2040's on-chip boot ROM functions.

It boots into a shell over USB CDC-ACM (i.e. it shows up on your computer as a serial port), with a flat file system on the onboard flash, a small `nano`-like text editor, and a C-like scripting language with `exec`-style native functions.

Total footprint: ~18KB of code, ~83KB of RAM (out of the RP2040's 264KB) — the whole thing is smaller than a JPEG photo.

## Directory layout

```
src/       firmware source: .c/.h/.s/.S files and linker scripts
tools/     build-time helper scripts (pad_checksum.py)
build/     intermediate build output (.o/.elf, boot2 staging files) -- safe to delete, regenerated by every build
release/   final flashable images (kernel.bin, kernel_flash.bin)
```

## Hardware

- RP2040 board with a good amount of onboard QSPI flash (this build assumes **8MB**; see [Changing the flash size](#changing-the-flash-size) if yours differs).
- The console LED code targets the Pimoroni Tiny 2040's onboard green LED (GPIO19, active-low) as a boot-progress indicator. Adjust `LED_PIN` in `src/usb.c` for other boards.

## Toolchain

You need:

- `arm-none-eabi-gcc` / `arm-none-eabi-objcopy` (the GNU ARM embedded toolchain)
- [`picotool`](https://github.com/raspberrypi/picotool) to load the built image over USB

On macOS with Homebrew:

```sh
brew install --cask gcc-arm-embedded   # or: brew install arm-none-eabi-gcc
brew install picotool
```

> **Known issue:** `picotool info` segfaults on picotool 2.3.0 (a null-deref in its RP2350 partition-table code path, which it shouldn't hit for RP2040 at all). Harmless — `picotool load` (what the build uses) doesn't touch that code path.

## Build & flash

There are two ways to run this: loaded into RAM each time (fast iteration, needs a reflash after every power cycle), or flashed once so it boots on its own from then on. Both share the same application code — only the boot path differs.

### RAM boot (development)

1. Put the board in BOOTSEL mode: hold the **BOOTSEL** button, plug in USB, release.
2. Run the VS Code build task ("Build Bare-Metal Kernel", the default build task — <kbd>Cmd+Shift+B</kbd>), or from the command line:

```sh
arm-none-eabi-gcc -c -mcpu=cortex-m0plus -mthumb src/crt0.s -o build/crt0.o
for f in main usb flash fs editor script; do
  arm-none-eabi-gcc -c -mcpu=cortex-m0plus -mthumb -O2 -ffreestanding -nostdinc -Isrc src/$f.c -o build/$f.o
done
arm-none-eabi-gcc -mcpu=cortex-m0plus -mthumb -T src/linker.ld \
  build/crt0.o build/main.o build/usb.o build/flash.o build/fs.o build/editor.o build/script.o \
  -o build/kernel.elf -nostdlib -lgcc
arm-none-eabi-objcopy -O binary build/kernel.elf release/kernel.bin
picotool load release/kernel.bin -t bin -o 0x20000000 -v -f -x
```

The kernel runs entirely out of SRAM (see `src/linker.ld`) — it's loaded directly into RAM and executed via `picotool`'s `-x` flag, rather than booting from flash. That means **every power cycle needs a reflash**; nothing is written to flash except your files (the filesystem persists across reflashes and power cycles, since it lives in a completely separate region of flash the kernel never touches for code).

### Persistent boot (boots on its own, survives power cycles)

1. Put the board in BOOTSEL mode.
2. Run the VS Code task **"Build & Flash Persistent (Boot from Flash)"**, or from the command line:

```sh
arm-none-eabi-gcc -c -mcpu=cortex-m0plus -mthumb src/boot2.S -o build/boot2.o
arm-none-eabi-ld -T src/boot2_link.ld build/boot2.o -o build/boot2.elf
arm-none-eabi-objcopy -O binary build/boot2.elf build/boot2_raw.bin
python3 tools/pad_checksum.py build/boot2_raw.bin build/boot2_padded.bin

arm-none-eabi-gcc -c -mcpu=cortex-m0plus -mthumb src/crt0_flash.s -o build/crt0_flash.o
for f in main usb flash fs editor script; do
  arm-none-eabi-gcc -c -mcpu=cortex-m0plus -mthumb -O2 -ffreestanding -nostdinc -Isrc src/$f.c -o build/$f.o
done
arm-none-eabi-gcc -mcpu=cortex-m0plus -mthumb -T src/linker_flash.ld \
  build/crt0_flash.o build/main.o build/usb.o build/flash.o build/fs.o build/editor.o build/script.o \
  -o build/kernel_flash.elf -nostdlib -lgcc
arm-none-eabi-objcopy -O binary build/kernel_flash.elf build/kernel_flash_body.bin

cat build/boot2_padded.bin build/kernel_flash_body.bin > release/kernel_flash.bin
picotool load release/kernel_flash.bin -t bin -o 0x10000000 -v -f -x
```

How this differs from RAM boot:

- **`src/boot2.S`** is a 256-byte second-stage bootloader prepended to the image. On every cold boot, the RP2040's on-chip ROM always looks for this at flash offset 0 (unless BOOTSEL is held) — it configures the QSPI flash chip for fast reads and jumps into the vector table right after it. This one targets Winbond W25Q-family chips (also compatible with several similar parts — W25Q16JV, AT25SF081, S25FL132K0); check your flash chip if you're on different hardware. `tools/pad_checksum.py` appends the checksum the ROM requires before it'll run it — **see the callout below, this checksum is not what you'd expect from `pico-sdk`.**
- **`src/linker_flash.ld`** splits the image: code/rodata execute in place from flash (XIP), while `.data` and a small `.ram_func` section get copied into RAM at boot (`src/crt0_flash.s` does the copying, alongside the usual BSS zeroing).
- **`.ram_func`** matters for correctness, not just performance: `flash_init`/`flash_erase`/`flash_program` in `src/flash.c` are tagged into this section because they briefly make flash unreadable while talking to the chip. That's harmless in the RAM-boot build (nothing lives in flash to lose), but once the kernel itself executes from flash, those specific functions have to run from RAM instead — otherwise the CPU loses its own instruction stream mid-erase.
- **TinyFS starts at flash offset 256KB** (`FS_BASE_OFFSET` in `src/fs.c`) instead of offset 0, reserving room for the kernel image itself. This applies to both boot modes (one on-flash format, regardless of which kernel image is currently running) — so files written under an older build with a different `FS_BASE_OFFSET` won't be found; format is needed once.

> **A real `pico-sdk` bug, found the hard way:** the official `pad_checksum` tool (`pico-sdk/src/rp2040/boot_stage2/pad_checksum`) computes a checksum that real RP2040 hardware does not accept as a standalone raw flash write — confirmed by testing a checksummed image directly against actual hardware (verified via `picotool` and independently via UF2 drag-and-drop, both rejected consistently) and cross-checking against the published CRC-32/MPEG-2 test vector (`"123456789"` → `0x0376E6E7`), which `pad_checksum`'s output does not match. The correct algorithm — confirmed here empirically on real hardware, and matching the standard CRC-32/MPEG-2 check value exactly — is a direct, non-reflected CRC-32/MPEG-2 (poly `0x04C11DB7`, init `0xFFFFFFFF`, no input/output reflection, no final XOR), computed MSB-first per byte. That's what `tools/pad_checksum.py` here implements. This presumably doesn't bite normal SDK users because the official boot2 images ship prebuilt and pre-checksummed in the SDK repo — `pad_checksum` itself may simply never get exercised end-to-end against real silicon in the normal build flow.

3. Connect: the board enumerates as a USB CDC-ACM serial device (`TinyOS Console`). On macOS:

```sh
screen /dev/cu.usbmodem1101 115200
```

(exact device path/number varies; check `ls /dev/cu.usbmodem*`). Any serial terminal at 115200 8N1 works.

## Shell

```
help                     list commands
sysinfo                  OS/CPU/RAM/flash summary
clear                    clear the screen
hello                    sanity check
ls                       list files/directories
cat <file>                print a file's contents
write <file> <text>      write text to a file (single line — see nano for anything longer)
mkdir <dir>              create a directory marker
rm <name>                delete a file or directory entry
mv <old> <new>            rename
nano <file>               open the text editor (see below)
run <file>                 run a TinyScript file (see below)
format                    wipe the filesystem
exit                      soft-disconnect USB and halt
```

### Filesystem (TinyFS)

A deliberately simple flat filesystem:

- One reserved sector holds a superblock + a fixed 32-entry directory table (flat namespace — no real nested directories; `mkdir` creates a directory *marker* entry, but paths like `docs/notes.txt` don't resolve into it).
- File data is appended sequentially into the rest of flash. There's no reclamation of deleted files' space — `rm` frees the directory slot but not the underlying flash bytes. Run `format` to reclaim everything if you fill it up.
- Max file size: 4KB (one flash sector) per file; max 32 files/directories total.

### `nano` editor

A small full-redraw screen editor, not the real GNU nano, but nano-shaped:

| Key | Action |
|---|---|
| Arrow keys | Move cursor |
| Backspace | Delete character before cursor |
| Enter | New line |
| **Ctrl+O** | Save |
| **Ctrl+X** | Exit |

Note it's **Ctrl+O** to save, not Ctrl+S — Ctrl+S is the classic terminal software-flow-control byte (XOFF), and most terminals/`screen` will silently eat it before it ever reaches the device.

## TinyScript

`run <file>` executes a small C-like scripting language. Integers and strings only (no floats, no arrays/objects) — this keeps the whole interpreter (lexer + recursive-descent parser + tree-walking evaluator) under ~1KB of code.

```js
function fact(n) {
  if (n <= 1) {
    return 1;
  }
  return n * fact(n - 1);
}

print("5! =", fact(5));

i = 0;
while (i < 5) {
  print("i =", i);
  i = i + 1;
}

name = "World";
print("Hello, " + name + "!");
```

- Variables are dynamically typed, declared on first assignment (no `var`/`let`).
- Functions get their own local scope (parameters + any variable assigned inside them); assigning inside a function never mutates a same-named global — it always creates/updates a local. Reads fall back to globals if no local exists.
- Recursion is supported up to a fixed call depth of 16.
- `while` loops are capped at 1,000,000 iterations as a runaway-script guard.
- Errors (parse errors, undefined variables, division by zero, stack overflow, etc.) print a message and abort the script — they don't crash the shell.

### Native functions

These call straight into the OS (the "exec functions"):

| Function | Description |
|---|---|
| `print(a, b, ...)` | Print args space-separated, with a trailing newline |
| `write(name, content)` | Write a file (via `fs_write`); returns `true`/`false` |
| `read(name)` | Read a file's contents as a string, or `nil` if missing |
| `exists(name)` | `true`/`false` |
| `len(s)` | String length |

Adding a new native function means adding one entry to the `natives[]` table in `src/script.c` — wrap any existing C function with the `value_t (*)(value_t *args, int argc)` signature.

## Architecture

| File | Role |
|---|---|
| `src/crt0.s` | RAM-boot vector table + reset handler; zeroes BSS, calls `main()` |
| `src/linker.ld` | RAM-boot linker script: places everything in SRAM (0x20000000) |
| `src/boot2.S` | Flash-boot second-stage bootloader: QSPI XIP bring-up, 256 bytes |
| `src/boot2_link.ld` | Throwaway linker script for compiling `boot2.S` to a flat binary |
| `tools/pad_checksum.py` | Pads/checksums `boot2.S`'s output the way the RP2040 ROM actually requires (see the callout above) |
| `src/crt0_flash.s` | Flash-boot vector table + reset handler; also copies `.data`/`.ram_func` out of flash before zeroing BSS |
| `src/linker_flash.ld` | Flash-boot linker script: code executes in place from flash (XIP), `.data`/`.ram_func` copied to RAM |
| `src/main.c` | Shell: command parsing/dispatch |
| `src/usb.c` / `usb.h` | Clock/PLL bring-up, RP2040 USB device controller, CDC-ACM enumeration and console I/O |
| `src/flash.c` / `flash.h` | QSPI flash access via the RP2040 boot ROM's function table (erase/program/read) — no bit-banging, no `pico-sdk` |
| `src/fs.c` / `fs.h` | TinyFS: superblock, directory table, append-only file data |
| `src/editor.c` / `editor.h` | The `nano`-like screen editor |
| `src/script.c` / `script.h` | TinyScript: lexer, parser, tree-walking interpreter, native function table |
| `src/stdint.h` / `string.h` | Minimal freestanding replacements (no libc) |
| `build/*` | Intermediate `.o`/`.elf` and boot2 staging files — regenerated by every build, safe to delete |
| `release/*.bin` | Final flashable images |

### Changing the flash size

`FS_FLASH_SIZE` in `src/fs.c` is derived from an 8MB total (`8u * 1024u * 1024u - FS_BASE_OFFSET`). If your board has a different flash chip, change that constant to match before writing enough data to hit the boundary — TinyFS doesn't currently probe the flash's JEDEC ID to detect size automatically.

## Known limitations

- Filesystem: flat namespace, no space reclamation on delete, 4KB max file size, 32 file limit.
- TinyScript: integers/strings only, no arrays or closures, functions don't support default/variadic arguments beyond the fixed 8-argument call limit.
- `picotool info` segfaults on 2.3.0 (see [Toolchain](#toolchain)) — use `picotool load`/`picotool version` instead.
- `src/boot2.S` targets Winbond W25Q-family flash specifically; a different chip vendor may need a different QSPI bring-up sequence.
